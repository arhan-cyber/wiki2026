Purpose of the software

In brief

Pre-flight is a free tool that checks whether the score used to rank candidate gene edits can tell the candidates apart, before anyone acts on the ranking. It is a check, not a search method. In the team’s own case, the score could not separate the best design from doing nothing. The tool has been used on that one case; there is no pass case and no use by another team yet.

Pre-flight tests whether the scoring function of a model measures anything before its output is acted upon.

When flux balance analysis (FBA) is used to choose knockouts, overexpression targets or other interventions, a scoring function forms part of the pipeline. Such a function can be entirely uninformative while producing output that appears valid, and COBRApy1 issues no warning. This occurred in the present project: the search was exact and the arithmetic correct, yet the top recommendation exceeded the unedited strain by 0.010 %, a difference that gas chromatography–mass spectrometry (GC-MS) cannot measure, and it was close to being passed to the wet lab. On the team’s own pipeline, the diagnostics script found this in about 15 minutes (Table 2). The tool has been run on one scoring function only (the team’s, which fails); it should work on any scoring function that exposes an evaluate(combo, target) method, but no other scoring function has been tested.

Pre-flight is not a search method. Brute force, greedy search and reinforcement learning address which candidate scores best. Pre-flight addresses whether “best” is meaningful. Both questions are relevant, and neither replaces the other.

Applicability

In brief

The tool is useful if a team ranks interventions by a score or is about to give a laboratory a list of strains to build. It is less useful if a team only reads a single product’s output or is curating a model.

Pre-flight is likely to be applicable if interventions are ranked by a score without verification that the score separates them by more than the assay resolution; if a ratio or profile across several products is optimised; if product exchange reactions retain the default bounds of the model; if a list of strains is about to be passed to a wet lab; or if machine learning is being considered for a combinatorial design problem.

It is likely to be less applicable if the flux of a single product is maximised at fixed growth and read directly (a setup that is much harder to mislead), or if a model is being curated and not used for design; in the latter case memote2 should be run instead, since it tests the model, which is a different task.

The six checks

In brief

Six automated checks each return pass, warning or fail with an explanation. Two of them (does doing nothing score as well as the best design, and can the score separate candidates at measurable resolution) were not found automated by the team in the other tools it read about. When either fails, the tool prints no ranked list.

Each check returns PASS, WARN or FAIL, with an explanation and a suggested remedy (Table 1).

Table 1. Pre-flight checks D1–D6: the condition detected, its consequence, and prior art.

Detects Consequence Novelty
D1 Doing nothing scores as well as the best design The score does not respond to the intervention Automated implementation not found by the team in the tools it read about
D2 All candidates lie within one measurement-resolution band The ranking is numerically real but experimentally untestable Automated implementation not found by the team in the tools it read about
D3 A weighted sum over several products returns only one of them A linear program visits vertices only; weights cannot produce a blend Not new: established methods (flux variability, alternate optima); Das and Dennis 19973 is cited for weighted-sum limits in multicriteria optimisation, and its relevance to D3 is the team’s reading
D4 Target exchange reactions are effectively unbounded The model produces the target more freely than a cell could Not new: implemented in memote
D5 The score tracks biomass rather than product Often intended, so the check asks and never fails Not new; Schuetz et al. 20074 is cited for the choice of objective in flux prediction, and its relevance to D5 is the team’s reading
D6 A scoring parameter changes nothing The corresponding constraint is not binding Not new: ordinary sensitivity analysis

Proposals are withheld. When D1 or D2 fails, the tool prints no ranked list and states the reason. The team read about eight strain-design tools (OptKnock,5 OptGene,6 OptForce,7 RobustKnock,8 cameo,9 MEWpy,10 OptFlux11 and StrainDesign12) and did not find a check of the scoring function before designs are emitted, or a refusal to output them. The tool versions, documents read and search terms were not recorded, and the tools were not run on a test case, so this is an absence of finding and not a verified survey; it should be tested by running one of these tools on the team’s null-intervention case.

The threshold that matters is the resolution of the assay, not that of the solver. The first version compared score differences with the solver tolerance and passed the defective pipeline. The thresholds are relative and tied to measurement resolution (DETECTABLE_RELATIVE_MARGIN = 1 %, MEASURABLE_RELATIVE_MARGIN = 5 %). These margins follow the assumed GC-MS replicate variation of 1–5 %, for which no source or team replicate data are cited. For an assay more precise than GC-MS, the values should be reduced.

The report printed for the team’s setup (run on 17 October 2026 from the repository) reads:

D2 landscape discrimination   FAIL   20 candidates, all inside one measurement band
D3 scalarization degeneracy   FAIL   weighted sum gave one product at every weight

Minimal adoption requirements

In brief

The tool needs only one function that returns a score for a set of edits. Checks that need more simply skip, so even a bare scoring function gets a useful report.

The checks require a single method, evaluate(combo, target) -> float. No COBRApy dependency is imposed, and the configuration system, evaluator and file layout need not be used. Checks that require more capability are skipped and do not fail, so that a bare scoring function still receives a useful report.

from preflight import run_diagnostics

class MyEvaluator:
    def evaluate(self, combo, target):
        return my_existing_scoring_function(combo, target)

report = run_diagnostics(
    MyEvaluator(),
    {"product_A": 0.7, "product_B": 0.3},
    candidate_combos=[("geneX",), ("geneY",), ("geneX", "geneY")],
)
print(report.to_text())
print(report.usable)  # False means any ranking is an artefact

For the full pipeline on another organism, the configuration file is copied and its values changed. Nothing in the package itself needs editing.

Installation and execution

In brief

The tool runs on Python 3.10 or newer with three packages and no separate solver. Four example scripts reproduce the team’s analyses in about 5 to 15 minutes each. The expected result of the diagnostics script is a failure, which is the demonstration.

Python 3.10 or newer is required, with three packages. No solver needs to be installed: GLPK is supplied with COBRApy.

Design choices and trade-offs

In brief

Five design choices were made, each with a cost: thresholds tied to the user’s assay, skipping instead of crashing, refusing instead of warning, one configuration file per organism, and brute force as the default search.

  • Assay-tied thresholds instead of solver tolerance. Trade-off: the resolution of the assay must be stated.
  • Skipping, not crashing, when a capability is missing. Trade-off: a bare scoring function receives fewer checks.
  • Refusal rather than warning for D1 and D2. Trade-off: a user who requires a list regardless must first correct the scoring.
  • All organism-specific settings in one YAML file. The package is organism-agnostic.
  • Brute force as the default search at the present scale (see Trust).

Architecture

In brief

The code is a small Python package with separate parts for the checks, an optional metabolic-model evaluator, configuration, search methods, a benchmark and a proposal sheet.

The package preflight/ contains diagnostics (the six checks), cobra_evaluator (an optional COBRApy-backed evaluator), config (the YAML-driven setup), filters, search and agent (brute force, greedy and reinforcement learning), benchmark (the search benchmark) and proposals (the proposal sheet, empty when D1 or D2 fails). Examples are in examples/ and tests in tests/.

Limits of applicability

In brief

The tool is not a search method, nothing about it has been validated against laboratory data, and its benchmark uses an artificial test problem. Its thresholds assume a particular measurement method and can be changed.

  • Pre-flight is not a search method.
  • Nothing here has been validated against wet-lab data. Every number is a statement about a model.
  • The search benchmark was run on a synthetic landscape, because the real landscape is flat and a comparison of strategies on a flat landscape measures nothing.
  • The reinforcement-learning agent is a simple linear Q-learner; the result shows that this agent was outperformed, not that the approach cannot work.
  • The thresholds assume GC-MS composition analysis with 1–5 % replicate error (an assumption with no cited source). A different assay requires different values, which are set in a single constant.
  • The tool has been run on one scoring function and one organism, both the team’s, and that scoring function fails. No scoring function that passes, and no third-party model, has been tried, so false-alarm behaviour is unknown. No other team has used or reviewed it.

Licence, code and testing

In brief

The code is open source under the MIT licence. The repository’s 26 tests pass. A second-person rerun on another operating system is recorded only in a team note and is not independently verifiable.

The software is released under the MIT licence and may be used, modified and incorporated into other pipelines. Repository: github.com/Siddhant-Chowdhary/igem-preflight (a team member’s GitHub account; a mirror on the iGEM GitLab is still to be made).

Testing. The repository holds 26 tests in three files (test_benchmark.py 7, test_filters.py 9, test_diagnostics.py 10). Running python -m pytest tests at commit f689baf on 17 October 2026 (Windows, Python 3.14) gave 26 passed. Running tests/test_diagnostics.py directly prints 10 passed, 0 failed; that is the count for that one file, which resolves the apparent discrepancy between ‘26 of 26’ and ‘10 passed’. A team note records a clean-install rerun by a second person on a different operating system with the same 26 passes and an identical feasibility frontier; the person and system are not recorded and this was not independently checked. Windows is the only system confirmed here; the install instructions cover Linux and macOS, but macOS has not been tested. No CI log is published.

Reports of cases in which a check fires, and of failure modes that are not covered by the tests, are welcome.
